# Grainline — PLAN

> 從「前端頁面 → 埋點 → 解析 → DW → 報表」的端到端沙盒。埋點設計一改，報表立即重算，並用**假資料上的數字**證明指標之間的 grain / 母體 / 血緣衝突。

## 0. 背景

電商報表常在前端埋點之前就開始規劃。前端、行銷、BI、DE 只能各自猜「到時候會有什麼資料」，分頭開會，一拖就是好幾個月。更麻煩的是，只有 DE 知道資料怎麼處理：BI 拿到的是整理好的表，看不出兩個指標的 grain 或 filter 互相衝突。例如：

- 週 UV ≠ 日 UV 加總（count distinct 不可加）
- 轉換率的分子和分母不是同一個母體（分子含 App、分母只算 Web；或分子算訂單數、分母算人數）

### 參考：PostHog 怎麼做

- 只存一張不可變的 `events` 表（event, distinct_id, timestamp, properties JSON），另用 `persons` / `person_distinct_ids` 做身分合併。
- Action、Insight（trends / funnels / retention）、HogQL view 都在**查詢時**對原始事件計算（schema-on-read），所以新定義會**回溯生效**，不需要 backfill。

**我們借用的：** 原始事件不可變；L2–L4 全部是「定義」（YAML），編譯成 DuckDB view，查詢時才算。切換埋點設計就能秒級反映到報表。

**PostHog 沒做、我們要補的：** 它沒有 grain 契約（週 UV 和日 UV 加總可並排而不警告），Trends 公式（A/B）也不檢查分子分母母體。這就是下面三條相容性規則的動機。

## 1. 目標

- **G1 單一真相：** 一套宣告式規格（YAML，放在 git），描述 L1–L4 四層，是前端、行銷、BI、DE 共用的契約。
- **G2 埋點前就有數字：** 依 L1 規格產生合成事件（persona 驅動的 session 模擬），在 DuckDB 實際算出報表。
- **G3 衝突用數字呈現：** 不只丟錯誤碼，而是「週 UV = 1,203；日 UV 加總 = 4,870；差異來自 3,667 次跨日重複造訪」。
- **G4 埋點設計可快速切換：** tracking plan v1 → v2 時，所有下游指標自動重算，並列出受影響的指標與數字 diff。
- **G5 看得見的因果：** 一個 demo 商店頁面，人點擊產生的事件和模擬器資料走同一個 ingest，業務能看到「我做了這個動作 → 報表這一格變了」，並點開計算路徑。

## 2. 非目標

- 不碰真實資料或 PII，不串接真實 GA / PostHog / Segment。**只用假資料。**
- 不追求生產級吞吐、串流即時性、多租戶、權限系統。
- 不做通用拖拉式 BI，不做任意 SQL 編輯器。
- 不用 Cube.js 或其他外部語意層（未來可加「匯出 Cube schema」）。
- 不做歸因模型、ML、預測。

## 3. 四層架構

每一層都是一份**契約**（YAML），而不是一張表；編譯後成為 DuckDB view。

| 層 | 名稱 | 擁有者 | 內容 | 執行物 |
|---|---|---|---|---|
| L1 | 事件契約 Tracking Plan | 前端、PM | event 名稱、在哪個行為時刻送出（`fires_on`）、property 與型別、值從哪裡來（`from`）、版本 | demo 前端 SDK、合成事件產生器、ingest 驗證 |
| L2 | 解析 / Staging | DE | 原始事件依 L1 驗證、轉型；session 切分；身分合併 | `raw_events`（不可變）→ `stg_*` view |
| L3 | 實體與事實模型 DW | DE | 實體（user、session、order）、事實表、**宣告 grain** 與主鍵 | `dim_*` / `fct_*` view |
| L4 | 指標與報表 | BI、行銷 | measure（宣告可加性）、filter、時間 grain、比率 = 分子 / 分母；報表 = 指標 × 維度 × grain | 編譯後的 SQL、報表 JSON |

```
demo 前端 / 模擬器 ──POST /ingest──▶ raw_events (immutable)
                                        │
                     L2 stg_* ◀─────────┘   ← 全部是 view，
                     L3 dim_* / fct_*         改 YAML 只需重新編譯，
                     L4 metrics / reports     不需要 backfill
```

## 4. 三條相容性規則

每條規則都有**靜態檢查**（看規格）和**數字證據**（在假資料上實算）。

### R1 可加性 / grain

每個 measure 必須宣告 `additive` / `semi_additive` / `non_additive`。non-additive（count distinct、比率）不可以從細 grain 加總到粗 grain。

- 例：`weekly_uv` 被定義成 `sum(daily_uv)` → 違規。
- 證據：同時算「直接在粗 grain 計算」與「細 grain 加總」，列出差值與造成差值的重複實體數。

### R2 比率母體

比率的分子與分母必須：

1. 計數單位是同一個實體（人 / 人，不是 訂單 / 人）；
2. 時間窗口相同；
3. 分子的 filter 包含分母的全部 filter（分子母體 ⊆ 分母母體）。

- 證據：列出「在分子但不在分母」的列數，以及比率是否可能 > 1。

### R3 血緣可達

L4 引用的每個欄位，都必須能經過 L3、L2 追到 L1 中已宣告的 event property，且型別相符。

- 能抓到「BI 假設會有、前端根本沒埋」的欄位。
- L1 改版時，輸出受影響的指標清單與 v1 / v2 數字 diff。
- 證據：血緣圖，標出斷鏈的位置。

### 第二階段：以終為始（YC demo）

M1–M5 解決的是「各部門對齊報表」。第二階段把重心拉高到**從賺錢的決策反推資料需求**：

```
L5 決策（選潛力商品…）   ← 以終為始，從這裡寫
  ↓ 反推：需要哪些指標
L4 指標（商品轉換率、曝光、毛利、庫存天數…）
  ↓ 需要什麼 grain 的表
L3 表（商品 × 日、訂單明細…）
  ↓ 需要哪些資料
L1 前端事件 ＋ 業務資料（訂單明細、商品、庫存）
  ↓
前端：哪個頁面、哪個時刻要埋什麼
```

分工：**規則引擎反推與驗證 → AI 提案（之後接 LLM）→ 人只把關錢的定義與會花錢的規則**。

已確認的決定（2026-10-11）：

- 商業模式：**自營品牌單店**（不做 Buy Box 這類多賣家平台指標）
- 自動化範圍：**產出建議清單，加上講清楚的模擬執行**（假設、算法、不確定性、限制都用白話寫出來），不自動動預算
- 順序：**先做確定性的規則反推，再接 LLM**
- 第一個打通 L5 → L1 的劇本：**潛力商品**（轉換好、曝光少）

里程碑：

- **M6：商品成為一等公民**：業務資料來源合約（訂單明細、商品、庫存，各有 grain 與擁有者）；曝光埋點；模擬器升級成有真相的市場（商品有真實吸引力、轉換傾向、趨勢、庫存；首頁版位與分類排序造成曝光偏誤）
- **M7：行銷指標庫（自營單店）**：商品 × 日 grain 的內建模板（曝光、點擊率、詳情瀏覽、加購率、商品轉換率、銷量、淨營收、毛利、庫存天數），R1–R3 延伸到商品 grain
- **M8：L5 潛力商品劇本與反推引擎**：劇本 YAML（評分、門檻、最少樣本、防呆）→ 建議清單與證據鏈；反推出需要的指標、表、事件與前端頁面行為，自動產出 tracking plan 提案與差異；用模擬器的真相評估每種埋點設計下的選品準確率
- **M9：模擬執行**：對建議清單做曝光介入，多個隨機種子、和對照組比較，用白話寫清楚假設、算法、不確定性與限制
- **M10：接上 LLM**：自然語言 → 劇本與指標 YAML（限定在指標庫內），引擎驗證不過就自動修正，白話解釋取捨
- **M11：傳統做法對照**：同一個「找潛力商品」需求，用多部門開會、文件往返的方式走一遍（時間軸、會議紀錄、互相矛盾的規格、上線後才發現的錯），和用這個工具走一遍並排比較，數字由模擬器算出
- **M12：後端資料是真相**（2026-10-12 加入）：訂單主檔、折扣碼主檔與使用紀錄；訂單數、營收、買家改從後端算；R4 業務規則（參照完整、有效期間、次數上限、金額一致）與前後端對帳
- **M13：埋點透視與會議模式**：demo 商店 hover 看埋點（參考 Amplitude Visual Labeling、Heap Visual Labeler）、點了指標跳動；一頁一重點的會議導覽；demo 商店付款也建立後端訂單
- **M14：語意層標準匯出**：保留 Grainline 的 YAML，匯出 Apache Ossie（OSI）與 Cube YAML，Grainline 獨有的部分放延伸欄位
- **之後**：報表卡紅黃燈、五層聯動視圖、L1 個資與同意標記、對外可存取的 demo 部署

### M1 設計決定

- **一層一個 YAML 檔**，放在 `specs/<project>/`：`l1_tracking_plan.yaml`、`l2_staging.yaml`、`l3_models.yaml`、`l4_metrics.yaml`，加上 `simulation.yaml`。每個檔案開頭寫明擁有者與語法。
- **信封欄位由系統固定**：`event_id, event_name, timestamp, anonymous_id, user_id, tracking_plan_version` 不在 L1 宣告；L1 只宣告 property。時間一律是台北時間、不帶時區。
- **L2 是設定，不是 SQL**：只有 session 逾時與身分合併策略（`stitch_to_user` / `anonymous_only`）。每個事件自動產生一個依 L1 型別轉好的 `stg_<event>`；L1 沒宣告的事件進 `stg_unknown_events`，不流到下游。
- **L3 不允許寫自由 SQL**：欄位只能 `from` 來源 stg view 的欄位（fact），或加上 `agg`（entity）。代價是表達力有限，換來的是每個欄位都能機械地追回 L1，R3 才做得到。
- **比率在報表 grain 上由分子、分母的彙總值相除**，不對比率本身加總。
- **合成資料可重現**：同一個 `seed` 產生完全相同的事件。property 值來源依序為 funnel 固定值 → bindings 情境值（商品、購物車、訂單）→ 依 L1 型別隨機。
- **名稱一律小寫 snake_case**，在 spec 層就擋掉，所以 compiler 可以直接把名稱放進 SQL，只需要跳脫值。

### M2 設計決定

- **L4 新增兩個可以「寫錯」的語法**，檢查器才有東西可抓：
  - `type: rollup`：先在 `from_grain` 算出某指標，再用 `agg` 彙總到報表 grain（例：週 UV = 日 UV 加總）。
  - ratio 的 `kind`：`rate`（分子 ⊆ 分母，例：轉換率）或 `per_unit`（每單位平均，例：客單價），兩者的 R2 檢查不同。
- **實際可加性由 measure 推導，不只看宣告**：`count_distinct / avg / min / max` 一律不可加；宣告成 additive 本身就是 R1 error。
- **R1 也檢查 grain 能否整齊切分**：日可以切進週和月，週不能切進月。
- **R2 的計數單位**：`count_distinct x` 的單位是 x 代表的實體；`count` 的單位是「該 model 的列」。分母的每個篩選都必須出現在分子。
- **R2 也做實測**：規格正確的 rate，仍會在假資料上量「分子不在同期分母裡」的實體數，有的話給 warning（範例中抓到跨午夜的 session）。
- **新增 `lineage` 模組作為單一真相**：每個 L3 欄位、L4 引用都追到 L1，帶型別與 enum。compiler 用它決定能建什麼，R3 用它產生 finding。
- **編譯改為容錯**：斷鏈的欄位從 model view 移除，用到它的指標、報表被跳過並列在 finding 的「影響」中；其他部分照常建立。`strict=True` 時直接報錯。
- **篩選值不在 L1 enum 裡算 R3 error 但不斷鏈**：SQL 跑得動，只是數字永遠是 0。
- **API 會偵測規格檔變動**：下一個請求自動重新產生假資料、重建倉儲（約 1 秒）。

### M3 設計決定

- **`POST /ingest` 只接收，不拒收**：只驗證信封格式（缺欄位才回 422），和 L1 不符的地方回傳 warning，事件照樣保存，由 L2 隔離或轉型（schema-on-read）。依 `event_id` 去重，SDK 重送是安全的。
- **`raw_events.source`** 區分 `sim`（模擬器）與 `live`（demo 商店）。live 事件另存在 `data/live_events_<project>.ndjson`，規格改動、倉儲重建時一併載入。
- **時間**：SDK 送 UTC ISO 字串，ingest 轉成台北時間、不帶時區（L1 約定）。
- **SDK 不綁定事件**：`track(name, props)` 由呼叫端決定；啟動時讀 `GET /tracking-plan`，送出前在瀏覽器端比對 L1。每個平台各有一個 `anonymous_id`（像不同裝置）；`identify` 後才帶 `user_id`。批次送出、失敗重送、頁面關閉時用 `sendBeacon`。
- **觸發時機照 L1 寫**：`add_to_cart` 在 API 成功後才送；`order_completed` 在付款成功頁載入時送，且同一張訂單重新整理不會再送（否則違反 `fct_orders` 的 grain）。
- **商店右側的埋點紀錄面板**：每個事件旁邊顯示 L1 的觸發時機、properties、瀏覽器端與伺服器的 warning；「伺服器解析（L2）」分頁顯示 person_id、session_id、是否被隔離。
- **刻意留一個未宣告的事件**：商品頁的「收藏」送出 `wishlist_add`，示範前端沒照契約埋點時會發生什麼。
- **前端部署**：Vite build 後由 nginx 提供，`/api` 轉發到 FastAPI；開發時用 Vite proxy。

### M4 設計決定

- **行為和埋點分開**（這是 M4 最大的改動）：模擬器與 demo 商店只回報「行為時刻」（moment，例如 `add_to_cart_click`、`add_to_cart_success`、`payment_success`、`order_complete_page_load`）和當下情境；L1 用 `fires_on` 決定哪些時刻送哪些事件、用 `from` 決定 property 取什麼值。換一份 tracking plan，商店程式碼和模擬的使用者行為都不用改。
- **真實世界的行為放在 `simulation.yaml` 的 `behavior`**：加入購物車 API 失敗率、折扣碼使用率、付款後沒等到成功頁、成功頁重新整理。不同的埋點設計「看到」這些行為的不同部分。
- **兩個版本是同一群人、同樣的行為**：行為用一組亂數、事件 id 與隨機 property 用另一組，所以送出的事件數不同也不會讓行為分岔。`/diff` 只用模擬資料，差異全部來自 tracking plan。
- **模擬資料截在觀察期結束的午夜**（像資料快照），最後一天不會只剩跨午夜的零星 session。
- **L1 有多個版本**：`specs/<project>/tracking_plans/v*.yaml`，各自有 `status`（current / proposal / retired）。所有 API 接受 `?plan=`，省略時用 current。每個版本一個倉儲，第一次用到時建立（約 1 秒）。
- **model 的來源事件不在 L1 不再是格式錯誤**，而是 R3 `missing_event`：換版本時這很常見，應該列出影響範圍而不是整個規格無法載入。
- **新增 grain 資料檢查（歸在 R1）**：L3 宣告的 grain 在資料上要成立。v2 在成功頁送訂單，重新整理造成重複 order_id，會被抓出來並列出受影響的指標。
- **property 可以宣告 `required: false`**：情境裡沒有值時不帶（例如沒用折扣碼），SDK 與 ingest 不會因此發 warning。
- **Console**（`/console`）：報表（圖表 + 表格，點指標名稱看 L4 → L1 計算路徑，含商店點擊的列每 3 秒更新）、相容性檢查（R1–R3 與證據明細）、版本差異（L1 改動、各指標數字差異與相關改動、每日比較圖、報表與 finding 的變化）。
- **圖表**：單一或兩條線，2px 線、十字準線與 tooltip、兩條線時有圖例與直接標示；兩個類別色經過色盲與對比檢查（淺色、深色各自驗證）；不連續的期間斷線。

### M5 設計決定

- **依角色調整 console 的導覽與預設頁**（右上「我是」，記在瀏覽器）；所有頁面都還是看得到，只是排序不同：
  - 業務／行銷 → 指標說明、報表
  - BI → 報表、指標說明、相容性檢查、版本差異
  - 前端／PM → 埋點清單、版本差異、相容性檢查
  - DE → 資料模型、相容性檢查、版本差異、報表
- **指標說明全部從規格與血緣自動產生**，不另外維護文件：一句話摘要；記錄（L1）→ 整理（L2）→ 建表（L3）→ 計算（L4）的白話步驟；要注意的地方（不可加、送出時機的副作用、只列出這個指標實際用到的欄位的 R1–R3 問題）。
- **「舉個例子」用一個模擬使用者的實際事件說明**：列出他在那一天（rollup 是那一週）的所有事件，標出哪些被算進來、他貢獻多少，再對照全站的值。挑人時優先挑能看出重點的：不重複人數挑有多筆事件的人、rollup 挑一週來好幾天的人、grain 有重複時挑有重複的人。
- **埋點清單**：每個事件什麼時候送（含送出時機的副作用）、每個欄位的型別與值從哪裡來、下游用到它的指標與報表；最上面列出「下游需要、這個版本還沒埋的」和「demo 商店送了、L1 沒宣告的」，以及 demo 商店收到的不符 L1 的事件統計。
- **資料模型**：L2 的身分與 session 規則（白話與設定值）、每個 model 的 grain、列數、grain 在資料上是否成立、每個欄位追到 L1 的哪裡、編譯後的 SQL。
- API：`GET /metrics/{name}/explain?example=N`、`GET /events`、`GET /models`，`GET /metrics` 加上摘要、問題數與用到的報表。

### M6 設計決定

- **L1 分成兩種合約**：前端事件（tracking plan）與業務資料來源（`l1_sources.yaml`：商品、訂單明細、每日庫存）。業務資料各自宣告 grain、欄位型別、擁有者；有身分欄位的（訂單明細）在 L2 套用同一套身分合併規則，補上 `person_id`。L3 model 用 `table:` 引用業務資料，和 `source:`（事件）擇一。
- **銷量、營收的真實來源是後端**：訂單明細在「後端建立訂單」時寫入，和埋點設計無關；換 tracking plan，業務資料完全一樣。新增「前端事件 vs 後端資料」報表，v1 兩者一致，v2 不一致。
- **曝光埋點**：新增行為時刻 `product_impression`（首頁精選、分類頁的商品卡片進入畫面），事件帶 `list_name` 與 `position`。商店用 IntersectionObserver，每次頁面載入每張卡片最多送一次。
- **有真相的市場**：每個商品有真實的吸引力、轉換傾向、上升趨勢、庫存；有些商品在期間中才上架。首頁 8 個精選與分類頁排序依 `legacy_rank`（舊排序），不看真實品質，造成曝光偏誤。使用者從看過的卡片裡依吸引力與位置點進商品，依商品的轉換傾向決定加購；沒庫存就加購失敗。
- **真相只留在模擬器**：`World.truth` 記錄每個商品的真實轉換傾向、曝光、是否為真正的潛力商品（轉換傾向前 25%、曝光後 50%），只給 M8 評估用，不會出現在任何 API。
- **所有 session 依時間先後處理**（priority queue），庫存才會照真實順序扣；同一個人的 session 不重疊。
- **業務資料的 grain 也檢查**（R1 `grain_duplicate`，subject `source:<name>`），重複時回頭找擁有者。
- **測試用 400 個訪客的小模擬**（demo 維持 1,500），結構與比例相同，測試時間維持在 40 秒內。

### M7 設計決定

- **內建行銷指標庫**（`api/app/library/marketing.yaml`，自營品牌單店）：13 個指標分成流量、商品漏斗、銷售、獲利、庫存。每個寫明定義、為什麼重要、對應的 Amazon 報表名稱（參考用，定義以指標庫為準）、grain，以及需要哪些前端事件（含送出時機與 property）、業務資料欄位、其他指標。專案的 L4 用同樣的名稱就算採用了指標庫的定義。
- **覆蓋檢查**（反推的前半段）：每個指標在目前規格下是「已可用／定義不同／資料夠但還沒定義／缺資料」，缺的每一項都寫明要找誰（前端或業務資料的擁有者）。v2 會顯示「新增事件 product_view」與「add_to_cart 要在 API 成功時送」。
- **L3 `lookup`**：從另一個 model 帶欄位（例如用 product_id 帶入成本）。被查的 model 必須一個 key 一列；grain 是多個欄位就是一對多，列為 R1 `lookup_fan_out`。欄位改叫 `by` 而不是 `on`，因為 YAML 會把 `on` 讀成 true。
- **L3 `expr`**：同一個 model 的其他欄位做四則運算（毛利 = 營收 − 件數 × 成本）。用小型文法解析器檢查，只允許欄位、數字、+ − × ÷、括號。
- **比率類型 `funnel`**：漏斗下一步 ÷ 上一步（點擊率、加購率、商品轉換率），不要求子集、允許件數加總；資料上大於 1 時給 warning，說明裡提醒「分子不一定來自分母」。
- **商品每週表現報表**：商品 × 週的曝光、瀏覽、點擊率、加購、件數、轉換率、營收、毛利、毛利率、缺貨天數；v2 因為沒有 product_view 而無法建立。

### M8 設計決定

- **L5 決策劇本**（`l5_decisions.yaml`）：決策對象（product_id）、輸入（指標庫的指標）、評分、規則（每條附白話理由）、前幾名。輸入必須可加，才能在時間窗口內加總（R1 延伸到決策層）；`p50` 這種門檻是所有候選對象的百分位。
- **潛力商品劇本**：分數 = 收斂後的商品轉換率 × 每件毛利（每次商品頁瀏覽的預期毛利）。瀏覽少的商品往全站平均收斂（prior_strength 40），避免「3 人看、2 人買」衝到第一；規則是曝光在中位數以下、至少 20 次瀏覽、缺貨不超過 2 天、毛利為正。
- **真相改成和目標一致**：真正的潛力商品 = 真實的「每次瀏覽預期毛利」（轉換傾向 × 每件毛利）前 25%、曝光後 50%。只看轉換率的話，評估標準和劇本目標不一致。
- **反推**：劇本 → 指標（指標庫）→ L3 表（含 lookup 相依）→ L1 事件（含行為時刻）與業務資料（含擁有者）→ 前端要在哪個頁面、哪個動作埋。缺的依擁有者彙整。
- **自動產生 tracking plan 提案**：依劇本需要的事件補齊目前的 plan——新增事件、修正送出時機（**換掉**而不是加上，否則同一事件在兩個時刻送會重複計算）、補 property——寫成下一個版本檔案（status: proposal）。v2 補成 v3 後劇本就能執行。
- **用真相評估**：前 k 名命中真正潛力商品的比例，和兩種傳統選法（賣最好的、首頁精選）比較；逐日重跑，看第幾天開始選得準。只用模擬資料，只揭露「是不是潛力商品」的標記，不揭露真相數值。實測兩個 seed、多組參數都是劇本 4/5、傳統選法 0/5。
- **最少瀏覽數是準確與速度的取捨**：門檻 10 時第 11 天起就選得準，門檻 20 要到第 20 天，但較可靠；預設 20。

### M9 設計決定

- **模擬器支援情境**（`Scenario`）：商品世界永遠由 simulation.seed 決定（同一份真相），情境只換使用者行為的隨機種子、往後模擬幾天、可以覆寫首頁精選；不產生前端事件時 14 天只要約 0.1 秒。原本的模擬結果完全不變。
- **模擬執行**：首頁精選裡過去每次曝光毛利最低的 5 格換成建議商品（表現好的保留；M11 時從「換掉後 5 格」改成這樣，因為後 5 格裡常有熱銷商品，換掉它們不公平也不合實務），模擬接下來 14 天。同一組隨機情境各跑「維持現狀」「照建議換」「隨機換」，差異就是效果；換 5 組情境重複，給範圍。
- **把「選得好」和「隨便換都會漲」分開**：目前的首頁精選不看商品好壞，所以隨機換也會漲。「照建議換 − 隨機換」在同一組情境逐次配對相減，才是劇本的貢獻。實測：照建議換毛利平均 +49.6 萬（+27.4 萬到 +66.5 萬，5/5 次增加），其中選得好的部分平均 +13.5 萬（4/5 次較好）。
- **誠實揭露代價**：被換下首頁的商品會少賣，總效果已經扣掉；商品表列出每個換上、換下商品的曝光、件數與毛利變化。
- **只用後端資料計算效果**（訂單明細 + 商品成本），不受埋點設計影響。
- **白話說明分四段**：假設、怎麼算、不確定性（含範圍與幾次增加）、限制（模擬世界、沒考慮長期影響與價格廣告季節、建議先做 A/B 測試）。結果依參數快取在倉儲上。

### M10 設計決定

- **分工**：Claude 把一句話的決策需求翻成 L5 劇本、用白話解釋取捨；規則引擎負責驗證（schema、輸入可加、反推需求、實際試跑）。不通過就把引擎的錯誤交回給 Claude 修正，最多 3 次；對話只往後加。
- **只能用指標庫**：structured outputs（`output_config.format` JSON schema）把指標名稱限定在指標庫的 enum 裡；系統提示標明每個指標可不可以當輸入（比率不行）。資料不夠時回 `feasible: false` 與缺的指標，不能自己發明。
- **模型**：`claude-opus-5-5`、effort `medium`；系統提示（指標庫、範例劇本）固定，開啟 prompt caching；預設開啟伺服器端 fallback（`fallbacks: "default"`），並處理 `refusal`、`max_tokens` 兩種 stop reason。
- **人把關**：結果只是預覽，按下儲存才附加到 `l5_decisions.yaml`（保留原本的註解），名稱重複會被擋下。
- **可以經 OpenRouter 呼叫**（2026-10-12 加入）：設了 `OPENROUTER_API_KEY` 就優先走 OpenRouter 的 Anthropic 相容端點（`https://openrouter.ai/api`，模型 `anthropic/claude-opus-5.5`），仍用官方 Anthropic SDK；Anthropic 專用的 fallback beta 參數不送，快取改標在系統提示上。走 OpenRouter 時只送 OpenRouter 的金鑰，即使也設了 Anthropic 金鑰也不會送出去（有測試鎖住）。理由：demo 用的金鑰外洩時，損失範圍比較好控制。`GRAINLINE_MODEL` 可以換模型。
- **沒有金鑰時功能顯示未設定**，其他功能照常；金鑰放在專案根目錄的 `.env`（不 commit，附 `.env.example`），由 docker compose 傳進 api。呼叫 Claude 時用獨立的 DuckDB cursor，不鎖住其他請求。
- **測試不呼叫真的 API**：用假的 client 依序回傳準備好的答案，驗證提案、引擎回饋修正、放棄、資料不足、拒絕、儲存、未設定。

### M11 設計決定

- **對照頁是 demo 的入口**（根網址 `/` → `/console/story`）：同一個「找潛力商品」需求，左邊傳統做法（開會、文件往返），右邊 Grainline（從決策往回推），下面是結果與「自己看看」的連結。
- **傳統做法的時間軸是示意**（約 11 週，依常見的跨部門流程假設），頁面上明確標示；但每一步造成的數字都由模擬器實際算出：同叫轉換率的兩種定義差多少、照前端提案（v2）埋點後加購灌水與訂單偏差、哪些報表做不出來、最後用「首頁放銷量前幾名」選中幾個真正的潛力商品。
- **Grainline 這一側列出每一步實際的計算秒數**，以及需要人做的步驟（DE 覆核簽核、前端照簽好的 tracking plan 埋點）。
- **結論要在不同市場都成立**：一個市場裡傳統做法有時候和劇本差不多（seed 42：傳統 +60.9 萬、劇本 +62.6 萬），所以頁面提供「在 6 個不同的模擬市場重複驗證」：每個市場的商品與使用者都不同，各模擬 3 次。實測 6/6 個市場劇本賺得比較多，平均每 14 天多 69.8 萬；劇本選中 3–5/5 個真正潛力商品，傳統做法都是 0。
- 對照結果與 6 個市場的結果都快取在倉儲上；第一次載入約 10 秒，6 個市場約 30 秒。

### M12 設計決定

- **前端事件只能證明「收到付款成功」，訂單以後端為準**。新增業務資料 `orders`（訂單主檔：狀態、通路、小計、折扣、運費、實付、折扣碼、建立／取消／退款時間）、`coupons`（折扣碼主檔，擁有者：行銷）、`coupon_redemptions`（使用紀錄；訂單取消時沖銷）。
- **主要指標改名與改來源**：`orders`、`revenue`、`buyers`、`aov`、`conversion_rate`、`refund_rate`、`discount_cost` 都從後端算（不含已取消；營收是實付金額）。前端事件算的改叫 `orders_reported`、`revenue_reported`（前端回報），只用來對帳。原本的前端訂單 model 改名 `fct_order_events`，`fct_orders` 是後端訂單主檔。訂單明細用 lookup 帶入訂單狀態，件數、商品營收、毛利都排除已取消。
- **換 tracking plan，後端訂單一筆都不會變**：v1/v2 差異裡 `orders`、`revenue` 的差是 0，只有 `orders_reported` 會偏。
- **R4 業務規則寫在業務資料合約裡**：`reference`（參照完整）、`within`（有效期間）、`limit`（次數上限，可加篩選；分組欄位是空的不計，例如未登入的訪客）、`match`（兩張表依 key 加總要一致）。每條附白話理由；違規要回頭找資料擁有者。
- **對帳也是 R4**：L4 的 `reconciliations` 宣告前端回報與後端真實數字（訂單數、訂單金額），差距超過容許比例就警告。
- **模擬器刻意產生後端 bug**：過期的折扣碼有時候被接受、每人使用上限有時候沒檢查。R4 抓到 42 筆過期使用（都是 9/7 過期的 SUMMER15）與 3 筆超過每人上限；關掉 bug 時 R4 沒有任何錯誤（沒有誤報）。也模擬取消（3%）與退款（4%），資料快照之後才發生的狀態變化看不到。
- 指標庫加上後端的訂單數、營收、退款率、折扣成本。

### M13 設計決定

- **demo 商店付款時由後端建立訂單**（`POST /shop/orders`）：依商品目錄計價、照規則驗證折扣碼（這條路徑沒有刻意的 bug：過期、未達門檻、用完、超過每人上限都拒絕並說明原因）、算運費，寫入訂單、明細與使用紀錄；前端拿到後端的訂單後才送付款成功事件。demo 的後端資料另存檔案、倉儲重建時載入，所有 tracking plan 版本都看得到；清除 demo 資料時一併清除。
- **埋點透視**（參考 Amplitude Visual Labeling、Heap Visual Labeler）：商店右上角的開關。有埋點的元素加紫色外框、沒被目前的設計記錄的加紅色虛線；滑鼠移上去看：什麼時候送、送哪個事件、每個欄位的值從哪裡來、會變成哪些指標、送出時機的副作用；沒被記錄時列出會讓哪些指標算不出來或定義不同。頁面載入的埋點放在標題下面。送出事件時左下角提示「這會變成哪些數字」。`/shop?overlay=1` 直接打開。
- **會議模式**（`/meeting`）：8 頁、一頁一個重點、字放大、方向鍵切換：問題 → 以終為始 → 看得到的埋點 → 前端提案的代價 → 選品 → 模擬執行 → 資料品質 → 下一步。數字都即時來自模擬器，每頁有連結打開實際畫面。
