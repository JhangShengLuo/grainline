# Grainline 重構設計（refactor 分支）

日期：2026-10-15　狀態：待使用者審閱

## 1. 要解決的痛點

電商公司自建埋點（打自家 API，規格放在 Excel）。行銷提出報表需求後，要經過 BI → DE → BI → 行銷 → 前端 → 行銷這樣來回，定版至少半年，有時十個月以上。根本原因：

- **抽象**：大家討論的是紙上規格。真正收進來的是 URL 後面一長串參數，加上巢狀 JSON；DE 只能憑想像模擬資料。
- **看不到層級**：一次瀏覽有多個商品，一張訂單有多個 SKU，一個人點過多個活動。欄位一 join 就乘開，但這很難向 BI 和行銷解釋。
- **沒有錨點**：每次討論都從零開始，沒有「電商標準做法」可以當起點，最後變成瞎子摸象。

## 2. 第一版目標（1 週）

用虛構電商做 demo（YC pitch），之後再拿到公司試用。第一批觀眾是 **BI 和行銷**。

只做三個問題：

| 問題 | 顧問預設做法 |
|---|---|
| 預算分配：哪個活動或渠道帶來最多銷售額 | 最後點擊歸因，訂單層粒度 |
| 助攻：哪些活動沒有直接成交，但帶人進站、之後才買 | 線性歸因，並與最後點擊比較 |
| 品類表現：哪些品類或 SKU 被看很多但轉換差 | SKU 層漏斗（曝光 → 瀏覽 → 加購 → 下單），不做歸因 |

另外支援首次點擊歸因，在切換歸因時當作對比。

### 非目標

- 不接真實資料，不匯入 Excel（屬於第二階段 A）
- 不做 AI 提案、會議模式、Ossie/Cube 匯出、潛力商品劇本、傳統比較頁、角色切換。這些在 refactor 分支上移除，main 分支保留
- 不做任意客製報表編輯器；客製需求先記錄在定案卡上

## 3. 畫面：資料流動，不是文字說明

**原則**：每個概念（乘開、歸因、缺欄位）都要用真實流動的（模擬）資料列和數字呈現。文字只用作短標籤。

單一頁面，一個可以縮放的畫布：

1. **頂端：問題選擇和顧問卡**。選三個問題之一。每個問題下面列出幾種行銷常見的說法（例如「我要看各活動 × 品類的銷售」），讓行銷認得出自己的需求。第一版不做自由輸入，也不用 AI 對應。顧問卡只有一行立場，例如「你想回答預算分配 → 預設最後點擊」，並附歸因切換鈕。
2. **主軸：旅程時間軸（橫向）**。每一步是一個前端動作，下面依序接著：
   - **頁面縮圖**：點擊後放大成可以操作的商店頁面；在頁面上的操作會在時間軸新增一步
   - **原始 hit**：真實長相的 URL 和 JSON，參數上色；缺少的參數標紅
   - **中繼表的列**：這筆 hit 變成哪幾張表的哪幾列，表頭標出粒度（「1 列 = 1 個 SKU」）
   - **儀表板的格子**：這些列最後算進哪一格
3. **儀表板**：該問題的標準報表。切換歸因時，金額在活動之間移動；開啟「用明細 join」時，會乘開的格子變紅，並顯示正確值。
4. **規模切換**：「模擬 N 位顧客」讓儀表板長出真實的規模；時間軸可以挑任一位顧客來看。
5. **定案**：按一下產生決議卡，內容包含：選了哪些數字、用哪種歸因、哪些格子會乘開以及正確的粒度、前端要在哪個事件補哪個參數。

## 4. 後端設計

### 保留並修改
- **產生器**（`generator.py`）：hit 改成真實格式，也就是 `ev`、`uid`、`sid`、`ts`、`page`、`utm_source`、`utm_medium`、`utm_campaign`，加上 `items` JSON 陣列。同一位顧客會跨多個 session、從不同活動進站。後端照舊產生 `orders` 和 `order_lines`。預設的 `purchase` hit **不帶** `utm_campaign`，讓缺欄位可以被示範。
- **編譯器、血緣、檢查**（`compiler.py`、`lineage.py`、`checks.py`）：保留。R1 抓乘開，R3 抓缺欄位，證據要能指回原始 hit 的參數路徑（例如 `items[].sku`）。
- **L2**：新增 URL 和 JSON 的解析 view，把 query string 和 `items` 展開成欄位或列。

### 新增
- **歸因模型**：`fct_touches`（一列 = 一次活動點擊，從 session 第一個 hit 的 utm 取得）、`fct_attributed_orders`（一列 = 訂單 × 活動 × 歸因方式，帶權重）。支援 last、first、linear，回溯期間（lookback）30 天。
- **問題庫**（`specs/shop/questions.yaml`）：三個問題的定義，包括顧問預設、可選的歸因、需要的事件和參數、儀表板指標與維度。
- **旅程 API**：`GET /journeys/{person_id}` 回傳每一步 → hits → 每筆 hit 產生的中繼表列 → 影響的儀表板格子。`GET /journeys/sample` 挑出具代表性的顧客（多次觸點、多 SKU 訂單）。
- **問題 API**：`GET /questions`、`GET /questions/{id}?attribution=last&fanout=false` 回傳儀表板資料，以及檢查結果（有／乘開／缺）。
- **定案 API**：`POST /questions/{id}/decision` 產生決議卡（Markdown）。

### 移除
AI 助手、Ossie/Cube 匯出、decisions、execution、story、圖書館（library）、diff 頁，以及它們的 API、測試和前端頁面。舊的 demo 商店改寫成縮圖加可以放大的頁面元件。

## 5. 驗收標準

- `docker compose up --build` 之後打開首頁，三個問題都能選，儀表板有數字
- 選一位樣本顧客，時間軸顯示每一步的頁面縮圖、原始 hit（真實 URL 格式）、中繼表列、儀表板格子；點縮圖可以放大操作，操作後時間軸多一步
- 預算分配：切換 last、first、linear，同一筆訂單的金額在活動之間移動；三種歸因下，各活動合計都等於總銷售額
- 開啟「用明細 join」，訂單數乘開並標紅；畫面上能看到 1 張訂單變成 N 列
- `purchase` 缺 `utm_campaign` 時，畫面上 URL 對應的位置標紅，定案卡寫出「請在 purchase 事件補上 utm_campaign」
- 品類漏斗：SKU 層的曝光 → 瀏覽 → 加購 → 下單，且被看很多但轉換差的 SKU 會被標出
- 整個 demo 沒有大段說明文字；每個結論都能點到對應的資料列
- pytest：產生器格式、URL 和 JSON 解析、三種歸因的權重加總為 1、乘開偵測、缺欄位偵測、旅程 API、定案卡；Vitest：時間軸元件
- 只用假資料

## 6. 一週拆分（概略）

1. 第 1 天：砍掉移除清單；產生器輸出真實格式的 hit 和多觸點；L2 URL/JSON 解析
2. 第 2 天：歸因中繼表和三種歸因；問題庫和問題 API
3. 第 3 天：旅程 API；檢查證據指回參數路徑；定案卡
4. 第 4–5 天：前端畫布、時間軸、縮圖放大頁、儀表板、切換開關
5. 第 6–7 天：串起來、潤飾 demo 腳本、測試
